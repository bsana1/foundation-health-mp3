# Verifying the frame count

The assignment suggests checking results with a tool such as `mediainfo`. We do
that, and go a step further: a committed corpus of MP3s spanning the format
space, each with an expected count pinned from a reference tool, checked in CI.

## The oracle: `ffprobe -count_frames`, not `mediainfo`

The two tools do not compute frame count the same way, and they disagree.

- **`ffprobe -select_streams a:0 -count_frames`** decodes the stream and counts
  the audio packets it actually reads (`nb_read_frames`). It excludes the leading
  Xing/Info/VBRI metadata frame, because the demuxer recognises it and never
  passes it to the decoder. This is a genuine count.
- **`mediainfo`'s `FrameCount`** is a _derived estimate_. For a VBR file it
  reports the frame count stored in the Xing header. For a CBR file it reports
  `round(duration × frame_rate)` — and that rounds up to include the Info frame
  on short files.

Concrete: a 3-second CBR file generated by ffmpeg —

|                                          |   count |
| ---------------------------------------- | ------: |
| physical frames (every valid MPEG frame) |     117 |
| the file's `Info` tag says               |     116 |
| `ffprobe -count_frames`                  | **116** |
| `mediainfo` FrameCount                   |     117 |

`ffprobe` matches the tag's own count and the decoder. `mediainfo` is one high.
On the _provided sample_ `mediainfo` happens to agree (6089) because that path
uses the Xing field — but the CBR estimate path does not. So we treat
`ffprobe -count_frames` as authoritative and `mediainfo` as a sanity check that
is allowed to differ.

Our definition — audio frames, excluding a leading Xing/Info/VBRI frame — is the
one `ffprobe` uses. See `.agent/DECISIONS.md`.

## The corpus

`test/fixtures/corpus/` — 20 files, ~2.5 MB.

**`generated/`** (ffmpeg / libmp3lame, `scripts/corpus-generate.sh`):

- CBR at 32, 64, 128, 192, 320 kbps @ 44100 Hz stereo
- CBR 128 kbps mono; CBR 128 kbps @ 48000 and 32000 Hz
- VBR (`-q:a 2` stereo, `-q:a 6` mono) over pink noise
- a ~0.4 s file (17 frames) and a 15 s file (576 frames)
- a file with the Xing frame stripped (`-write_xing 0`) — count is _every_ frame
- a file with a ~47 KB embedded cover image (ID3v2 tag larger than one chunk)
- **reject cases:** MPEG-2 LSF, MPEG-2.5, and a WAV with an `.mp3` name

**`real/`** (`scripts/corpus-fetch.sh`, trimmed with `-c copy`, see
`test/fixtures/corpus/CREDITS.md`):

- two SoundHelix clips — real LAME, CBR 192 kbps, one with the Xing frame, one
  without
- a samplelib.com clip — real LAME 3.100, CBR 128 kbps

## Results

`countMp3Frames` matches `ffprobe -count_frames` on **all 17 countable files**,
and rejects all 3 out-of-scope files with the right error. `mediainfo` agrees on
the longer and real files and is `+1` on the short generated CBR ones, as
expected.


## Running it

```bash
npm run corpus:verify            # check the committed corpus against manifest.json + the tools
npm run corpus:verify -- --write # regenerate manifest.json from current behaviour (after adding files)
npx tsx scripts/corpus-verify.ts ~/Music   # ad-hoc: point it at your own files
```

`npm test` also runs `test/mp3/corpus.test.ts`, which asserts `countMp3Frames`
against `manifest.json` with no external tools — so the regression gate works in
CI without ffmpeg installed.
